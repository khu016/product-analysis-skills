# 证据门槛与取证协议

## 一手证据

一手证据是能够直接观察目标产品行为或实现的材料。

| 来源 | 可以证明 | 不能单独证明 |
|---|---|---|
| 连续截图 | 可见文案、组件、状态、资产和时序 | 被遮挡交互、后台实现、未截图的失败路径 |
| 录屏 | 操作顺序、反馈、等待、跳转和部分失败恢复 | 未展示的内部调用和长期状态 |
| 已登录真实页面 | 当前账户和项目的可见行为 | 其他用户、其他版本或所有异常分支 |
| 原始代码与测试 | 可实现的分支、字段、接口和状态规则 | 线上是否启用、调用是否成功、用户实际经历 |
| 日志或结构化数据 | 已记录事件、工具结果、时序和状态 | UI 是否正确展示、用户是否看见或理解 |
| 产品宣传材料 | 产品自述、定位和承诺 | 真实执行流程、结果质量和故障处理 |

## 完整性检查

先将用户目标改写成一个可验证问题，再判断证据是否覆盖它。

### 必须明确

- 目标产品或代码库
- 要拆解的功能、流程或 Agent
- 用户角色和入口
- 期望交付深度
- 可读取的证据来源
- 允许和禁止的操作

### 范围覆盖

完整流程至少需要看到以下关键点中的相关部分。

- 起点和初始状态
- 用户输入或任务定义
- 产品第一次回应
- 参数、方案或确认门
- 执行中反馈
- 资产或结果出现
- 修改、返回或重新选择入口
- 至少一个终点状态
- 已出现的失败、中断、余额、权限或状态冲突

不要制造不存在的异常。页面没有异常样本时标记为尚未确认。

## 门槛决策

### 通过

证据足以回答用户限定的问题。开始编号并拆解。

### 部分通过

证据足以回答一部分。明确可回答范围和缺口，在用户没有要求等待时，可交付局部报告。不得把局部观察写成全产品结论。

### 不通过

只有产品名、宣传页、零散结论或无法打开的链接。停止分析并索取最小补充材料。

建议索取顺序。

1. 目标流程从进入到结果的连续截图或录屏。
2. 关键页面的展开状态、错误提示和资产详情。
3. 若研究实现，再索取对应代码、日志或数据结构。

## 证据冲突

同一任务出现多套状态时，不选一个作为真相。

| 冲突编号 | 状态 A | 状态 B | 时间关系 | 能确认的事实 | 不能确认的原因 | 下一步取证 |
|---|---|---|---|---|---|---|

常见冲突包括自然语言说完成但资产不存在、画布有结果但资产库为空、任务列表无任务但聊天仍等待确认、工具返回成功但状态写入失败。
